## Qué ocurre en esta captura
Se visualiza la actualización y verificación de Moodle en Docker y las pruebas locales de conectividad HTTP/HTTPS:
1. Diff de `compose.yaml`:
   - El mapeo de puertos se restringe de `"192.168.50.1:8080:8080"` a `"127.0.0.1:8080:8080"` (cerrando el acceso no cifrado desde la red LAN).
   - Se actualiza `MOODLE_URL` a `https://aulavirtual.ctcr` y se añade `MOODLE_SSL_PROXY: "yes"`.
2. Estado de los contenedores con `sudo docker compose ps`, mostrando `proyecto-moodle-db-1` y `proyecto-moodle-moodle-1` ambos en estado `healthy`.
3. Verificación de la URL efectiva dentro de Moodle ejecutando PHP en el contenedor:
   `echo $CFG->wwwroot` devuelve estrictamente: `https://aulavirtual.ctcr` y `$CFG->sslproxy: '1'`.
4. Prueba de petición HTTPS con `curl -k -I --resolve aulavirtual.ctcr:443:192.168.50.1 https://aulavirtual.ctcr`:
   - Código de estado: `HTTP/1.1 200 OK`.
   - Cabecera de servidor: `Server: nginx/1.28.3 (Ubuntu)`.
   - Cookie segura: `Set-Cookie: MoodleSession=...; secure; HttpOnly; SameSite=Lax`.
5. Prueba de redirección HTTP con `curl -I http://192.168.50.1 -H "Host: aulavirtual.ctcr"`:
   - Código de estado: `HTTP/1.1 301 Moved Permanently`.
   - Destino: `Location: https://aulavirtual.ctcr/`.

---

## Interpretación y límite
- **Lo que prueba:** Confirma que el contenedor de Moodle adoptó la nueva URL base con proxy SSL activado, que Nginx actúa efectivamente como proxy inverso comunicándose con Moodle en loopback `127.0.0.1:8080`, y que la redirección forzosa a HTTPS opera de forma impecable.
- **Lo que NO prueba:** No prueba la experiencia de usuario final en el navegador cliente de Mint; para ello se complementa con EV-069 y EV-070.
