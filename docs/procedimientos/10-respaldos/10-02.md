- **[`scripts/backup-db.sh`](../../../scripts/backup-db.sh)**: script versionado del dump SQL y retención con temporales.
- **[`infra/cron/moodle-backup.cron.example`](../../../infra/cron/moodle-backup.cron.example)**: programación y ruta que deben adaptarse al host.

**Lugar de ejecución:** terminal de Ubuntu Server (no la terminal del host Windows ni del contenedor, salvo cuando el comando sea `docker compose exec`). Confirmar direcciones reales y el estado actual de la VM antes de copiar comandos.

**Relación con el estado existente:** si el servicio ya está configurado, **no recrearlo por inercia**. Comparar con el archivo realmente activo; modificar solo campos necesarios, con copia, rollback y prueba posterior.

## Propósito del paso y contexto operacional

Respaldo y restauración: dump SQL, retención, datos de Moodle y ensayo separado sin destruir producción de laboratorio.

Este archivo corresponde **exclusivamente al paso 10-02**, con comandos históricos literales y mejoras razonadas. En una **VM ya configurada** se inspeccionan primero los servicios y datos; no se vuelven a crear credenciales ni volúmenes. Los resultados observados en las capturas pertenecen a la sesión que los originó, no al conjunto de cinco integrantes.

## Comprobación recomendada y salida a documentar

Comprobar `sudo crontab -l`, archivo `moodle_*.sql.gz` no vacío, `gzip -t`, restaurar `moodle_restore_test`, contar tablas y comprobar archivos moodledata con procedimiento aparte.

Registrar el resultado exacto, fecha, sistema y si la prueba pasó o falló. Para un cambio de configuración conservar el archivo anterior y ejecutar la validación sintáctica antes de reiniciar el servicio. La **ruta versionable recomendada** está explicada en [`infra/`](../../../infra/README.md), sin sustituir los comandos originales que aparecen abajo.

## Antes de ejecutar

- [ ] Identificar VM, interfaz e IP actual; no asumir la IP de otra persona.
- [ ] Inspeccionar el estado actual del servicio. Si hay datos o volúmenes existentes, respaldarlos antes de cambios.
- [ ] Registrar fecha, integrante responsable, revisor y versión vigente en la sesión de bitácora.

## Procedimiento completo y comandos originales

Primero:

```
cd ~/proyecto-moodle
```

Creá:

```
nano respaldo.sh
```

Pegá:

```
#!/bin/bash

set -euo pipefail

umask 077

PROJECT_DIR="$(cd "$(dirname "$0")" && pwd)"
BACKUP_DIR="/var/backups/moodle"
FECHA=$(date +%Y-%m-%d_%H-%M-%S)

cd "$PROJECT_DIR"

# Cargar las credenciales de la base de datos
set -a
source .env
set +a

mkdir -p "$BACKUP_DIR"

# Crear una copia de seguridad comprimida
docker compose exec -T \
    -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
    db mariadb-dump \
    -u root \
    --single-transaction \
    --quick \
    --routines \
    --events \
    moodle \
    | gzip > "$BACKUP_DIR/moodle_$FECHA.sql.gz"

# Comprobar que el archivo no esté vacío
test -s "$BACKUP_DIR/moodle_$FECHA.sql.gz"

# Comprobar la integridad del archivo comprimido
gzip -t "$BACKUP_DIR/moodle_$FECHA.sql.gz"

# Conservar solamente los últimos 7 días de copias
find "$BACKUP_DIR" \
    -type f \
    -name "moodle_*.sql.gz" \
    -mtime +7 \
    -delete

echo "Respaldo completado: $FECHA"
```

Guardá.

El script utiliza una ruta relativa a su propia ubicación, así que funciona dentro del directorio del proyecto sin depender de que alguien esté ubicado manualmente allí.

## Correcciones y precauciones aplicables

La guía original crea un SQL en /var/backups, pero la versión corregida `scripts/backup-db.sh` emplea un archivo temporal seguro y validación del gzip. Una copia SQL no respalda `moodledata` ni necesariamente la configuración completa.
