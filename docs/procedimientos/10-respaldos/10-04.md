**Relación con el estado existente:** este paso genera un archivo nuevo en `/var/backups/moodle/` con fecha y hora actual sin alterar ni borrar las bases de datos activas.

## Propósito del paso y contexto operacional

Antes de delegar la ejecución periódica al demonio Cron, es indispensable realizar una prueba de ejecución manual de extremo a extremo. Este paso comprueba:

1. Que el script se ejecuta correctamente bajo privilegios de `sudo` sin requerir entrada interactiva por consola.
2. Que la conexión hacia el contenedor Docker de MariaDB (`db`) se establece de forma limpia y transparente mediante `docker compose exec -T`.
3. Que el volcado de la base de datos `moodle` se transmite por la tubería y genera un archivo comprimido no vacío en `/var/backups/moodle/`.
4. Que el archivo resultante cumple estrictamente con el formato gzip y pasa la prueba de comprobación de suma de verificación de bloques (`gzip -t`).

## Comprobación recomendada y salida a documentar

1. Ejecución del script:
   ```bash
   sudo ./respaldo.sh
   ```
   Salida esperada:
   ```
   Respaldo completado correctamente: YYYY-MM-DD_HH-MM-SS
   ```

2. Listado de archivos generados y verificación de tamaño:
   ```bash
   sudo ls -lh /var/backups/moodle
   ```
   Debe mostrar el archivo `ctcr_moodle_*.sql.gz` con un tamaño aproximado de entre 350 KB y 450 KB.

3. Comprobación de integridad del archivo comprimido:
   ```bash
   sudo sh -c 'gzip -t /var/backups/moodle/*.sql.gz && echo "Integridad OK"'
   ```

## Antes de ejecutar

- [ ] Verificar que el contenedor MariaDB está en estado `healthy` (`docker compose ps`).
- [ ] Confirmar que el directorio `/var/backups/moodle` tiene permisos `0700`.
- [ ] Verificar que `respaldo.sh` tiene permisos `0700`.

## Procedimiento completo y comandos originales

1. Ubicate en la carpeta del proyecto Moodle:

   ```bash
   cd ~/proyecto-moodle
   ```

2. Ejecutá manualmente el script con privilegios de superusuario:

   ```bash
   sudo ./respaldo.sh
   ```

   El comando tardará unos segundos mientras extrae las 494 tablas de MariaDB y las comprime. Deberá finalizar imprimiendo:
   ```
   Respaldo completado correctamente: 2026-10-30_16-46-51
   ```

3. Verificá los archivos creados en el directorio protegido:

   ```bash
   sudo ls -lh /var/backups/moodle
   ```

   Se observará un archivo similar a:
   ```
   -rw------- 1 root root 384K Oct 30 16:46 ctcr_moodle_2026-10-30_16-46-51.sql.gz
   ```

4. Verificá la integridad del archivo comprimido:

   ```bash
   sudo sh -c 'gzip -t /var/backups/moodle/*.sql.gz && echo "Integridad OK"'
   ```

   Debe devolver `Integridad OK` sin advertencias de bloques truncados o datos corruptos.

## Correcciones y precauciones aplicables

- **Diagnóstico del incidente INC-012 (Comodines bajo `sudo`):**
  Al ejecutar `sudo gzip -t /var/backups/moodle/*.sql.gz` directamente desde la sesión de un usuario no privilegiado (`criss`), el intérprete Bash evalúa el comodín `*` antes de transferir el comando a `sudo`. Dado que el usuario normal carece de permisos de lectura sobre `/var/backups/moodle` (`0700 root:root`), la expansión falla silenciosamente y Bash pasa la cadena literal con asterisco, arrojando el error `gzip: /var/backups/moodle/*.sql.gz: No such file or directory`.
  **Solución:** Delegar la evaluación a una subshell de root mediante `sudo sh -c 'gzip -t ...'` o pasar la ruta absoluta exacta del archivo resuelto.
- **Integridad no es restauración:** Un archivo comprimido con integridad válida (`gzip -t`) garantiza que no está corrupto a nivel de bytes comprimidos, pero no demuestra que la base de datos se pueda importar sin errores relacionales. La prueba formal de recuperación se ejecuta en el subpaso 10-06.
