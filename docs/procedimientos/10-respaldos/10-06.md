# PASO 10.06 — Probar una restauración sin dañar Moodle

> **Naturaleza:** procedimiento reproducible derivado íntegramente de la guía compartida, con correcciones para el repositorio. **No implica que el paso esté verificado en todas las máquinas.**
>
> **Origen:** `docs/fuentes/GUIA-HISTORICA-INTEGRA.md`; capturas reales de la última bitácora cuando existen.

## Archivos relacionados y por qué importan

- **[`scripts/backup-db.sh`](../../../scripts/backup-db.sh)**: script versionado del dump SQL y retención con temporales.
- **[`infra/cron/moodle-backup.cron.example`](../../../infra/cron/moodle-backup.cron.example)**: programación y ruta que deben adaptarse al host.

## Propósito del paso y contexto operacional

Demostrar la efectividad real de la política de respaldo mediante una **prueba de recuperación ante desastres (DRP — Disaster Recovery Plan)** en un entorno estrictamente aislado, sin comprometer ni interrumpir la disponibilidad de la base de datos de producción `moodle`.

En administración de sistemas y gobernanza de TI, un axioma fundamental establece que *un respaldo no existe hasta que su restauración haya sido verificada de forma concluyente*. En este subpaso se ejecuta la restauración controlada del último volcado SQL generado sobre una base de datos temporal e independiente denominada `moodle_restore_test`, se coteja la paridad estructural completa (494 tablas de esquema de Moodle 4.5.15) y se verifica la preservación íntegra de entidades institucionales clave (cursos departamentales, cuestionarios y cuentas de usuarios), procediendo finalmente con el desmontaje ordenado de la base de prueba mediante `DROP DATABASE moodle_restore_test;`.

## Comprobación recomendada y salida a documentar

1. Creación de la base de ensayo con juego de caracteres `utf8mb4` y cotejo `utf8mb4_unicode_ci`.
2. Selección determinista del respaldo más reciente en `/var/backups/moodle/`.
3. Inyección directa del flujo descomprimido mediante tubería sin asignación de pseudoterminal (`docker compose exec -T`).
4. Consulta analítica en `information_schema.tables` contrastando el conteo de tablas entre `moodle` y `moodle_restore_test` (debe arrojar exactamente 494 tablas en ambas).
5. Consultas de integridad sobre registros críticos (`mdl_course`, `mdl_user`).
6. Eliminación limpia de la base de prueba y confirmación de que la base principal `moodle` permanece intacta.

## Antes de ejecutar

- [ ] Confirmar que el servicio MariaDB se encuentra en ejecución saludable (`docker compose ps db`).
- [ ] Verificar la existencia de al menos un volcado íntegro en `/var/backups/moodle/` (`sudo sh -c 'ls -lh /var/backups/moodle/*.sql.gz'`).
- [ ] Asegurarse de que el script o comando de restauración **nunca** apunte a la base activa `moodle`.
- [ ] Inspeccionar que haya suficiente espacio en disco en la partición `/var` para alojar temporalmente la base restaurada.

## Procedimiento completo y comandos originales

Bajo ninguna circunstancia se debe restaurar un volcado de prueba sobre la base de producción activa en una plataforma operativa de producción o laboratorio. Una sobrescritura accidental destruiría sesiones activas, transacciones en curso y modificaciones recientes de los cursos.

Por ello, se implementa una base de datos paralela y efímera:

1. Ingresá al directorio raíz del proyecto Moodle:

   ```bash
   cd ~/proyecto-moodle
   ```

2. Cargá las variables de entorno operativas (incluyendo `DB_ROOT_PASSWORD`):

   ```bash
   set -a
   source .env
   set +a
   ```

3. Creá la base de datos de prueba con soporte completo para Unicode y emojis:

   ```bash
   sudo docker compose exec -T \
     -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
     db mariadb -u root \
     -e "CREATE DATABASE IF NOT EXISTS moodle_restore_test CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
   ```

4. Identificá de forma determinista la ruta absoluta del respaldo más reciente en el almacenamiento local:

   ```bash
   BACKUP=$(sudo find /var/backups/moodle \
     -name 'ctcr_moodle_*.sql.gz' -o -name 'moodle_*.sql.gz' \
     -type f \
     -printf '%T@ %p\n' \
     | sort -nr \
     | head -1 \
     | cut -d' ' -f2-)
   ```

5. Confirmá que la variable `$BACKUP` apunta al archivo correcto:

   ```bash
   echo "Respaldo seleccionado para restauración: $BACKUP"
   ```

   Debe imprimir una ruta válida terminada en `.sql.gz` con permisos legibles para root.

6. Ejecutá la restauración mediante tubería continua de descompresión e importación:

   ```bash
   sudo gzip -dc "$BACKUP" | \
   sudo docker compose exec -T \
     -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
     db mariadb -u root moodle_restore_test
   ```

   > [!NOTE]
   > La opción `-T` en `docker compose exec` desactiva la asignación de un pseudo-TTY, evitando que secuencias de escape de terminal o saltos de línea `CRLF` interfieran con la lectura del flujo binario/SQL.

7. Validá la paridad estructural comparando el número total de tablas entre ambas bases:

   ```bash
   sudo docker compose exec -T \
     -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
     db mariadb -u root \
     -e "SELECT table_schema, COUNT(*) AS total_tablas FROM information_schema.tables WHERE table_schema IN ('moodle','moodle_restore_test') GROUP BY table_schema;"
   ```

   **Salida esperada:**
   ```
   +---------------------+--------------+
   | table_schema        | total_tablas |
   +---------------------+--------------+
   | moodle              |          494 |
   | moodle_restore_test |          494 |
   +---------------------+--------------+
   ```
   Ambas bases deben arrojar idéntico número de tablas (494 en Moodle 4.5.15 LTS), evidenciando que no hubo omisión de esquemas ni llaves foráneas no resueltas.

8. Validá la persistencia de registros curriculares e institucionales clave:

   ```bash
   sudo docker compose exec -T \
     -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
     db mariadb -u root moodle_restore_test \
     -e "SELECT id, shortname, fullname FROM mdl_course; SELECT id, username, email FROM mdl_user WHERE deleted=0;"
   ```

   Debe reflejar la presencia de los 3 cursos departamentales (`CTCR-ADM-101`, `CTCR-DOC-101`, `CTCR-INF-101`), el curso inicial del sitio y la totalidad de los usuarios institucionales creados durante el Paso 6.

9. Una vez registrada la evidencia fotográfica y textual de la prueba, eliminá exclusivamente la base de ensayo:

   ```bash
   sudo docker compose exec -T \
     -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
     db mariadb -u root \
     -e "DROP DATABASE moodle_restore_test;"
   ```

   > [!CAUTION]
   > Verificá minuciosamente el comando antes de presionar enter. Jamás ejecutes `DROP DATABASE moodle;` en este servidor.

## Correcciones y precauciones aplicables

- **Sintaxis de Docker Compose y TTY (`-T`):** Si se omite `-T`, docker intentará emular un terminal interactivo para una tubería estándar `stdin`, lo que provoca advertencias como `the input device is not a TTY` y puede corromper paquetes de datos en volcados voluminosos.
- **Patrones de búsqueda en find:** Dado que los scripts institucionales utilizan el prefijo `ctcr_moodle_*.sql.gz` y la guía teórica mencionaba `moodle_*.sql.gz`, el comando de búsqueda incluye una disyunción (`-o`) para localizar el volcado más reciente sin importar la convención exacta del prefijo.
- **Aislamiento transaccional:** La prueba de restauración se ejecutó sin detener el contenedor de MariaDB ni interferir con la navegación activa de los usuarios en `https://aulavirtual.ctcr`.
