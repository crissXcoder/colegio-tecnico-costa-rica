## Propósito del paso y contexto operacional

Delimitar formalmente el alcance de la estrategia de respaldo del Colegio Técnico de Costa Rica, distinguiendo con precisión técnica entre la información relacional alojada en el motor de base de datos MariaDB y los datos binarios no estructurados que residen en el sistema de archivos del volumen Docker `moodledata`.

En la arquitectura de Moodle LMS, los datos se dividen en dos capas complementarias pero desacopladas:
1. **Capa Relacional (Base de Datos MariaDB):** Contiene la lógica del sistema, cuentas de usuario, hashes de contraseñas, roles, estructura de categorías y cursos, inscripciones de cohortes, banco de preguntas de cuestionarios, intentos de evaluación, calificaciones numéricas y bitácoras de auditoría. Es respaldada de forma compacta y atómica mediante `respaldo.sh` y Cron diario a las 02:00 AM.
2. **Capa de Archivos Binarios (`moodledata`):** Contiene los recursos físicos subidos por docentes y estudiantes (PDFs, imágenes de perfil, paquetes SCORM, tareas enviadas, caché de plantillas Twig/Mustache y sesiones de usuario cuando no se usa Redis/DB).

Comprender esta distinción permite a los administradores del CTCR diseñar políticas de contingencia con métricas de **RPO (Recovery Point Objective)** y **RTO (Recovery Time Objective)** realistas y escalables.

## Procedimiento completo y comandos originales

El respaldo obligatorio programado en los subpasos 10-01 a 10-06 cubre el 100% de la base de datos MariaDB (`ctcr_moodle_*.sql.gz`), satisfaciendo los requisitos de evaluación académica y recuperación de configuraciones.

Para una recuperación catastrófica integral (*Bare-Metal / Total LMS Disaster Recovery*), se debe salvaguardar periódicamente el volumen de archivos `moodledata`. El procedimiento recomendado es el siguiente:

1. Ingresá al directorio del proyecto:

   ```bash
   cd ~/proyecto-moodle
   ```

2. Detené temporalmente el contenedor de la aplicación web de Moodle:

   ```bash
   sudo docker compose stop moodle
   ```

   > [!IMPORTANT]
   > Al detener el contenedor web de Moodle se congelan las escrituras sobre el sistema de archivos, garantizando que los archivos binarios y los metadatos en disco se mantengan en un estado 100% consistente durante el archivado. El contenedor de base de datos `db` puede continuar en ejecución.

3. Listá los volúmenes de Docker para corroborar el nombre del volumen asignado por Docker Compose:

   ```bash
   sudo docker volume ls
   ```

   En este despliegue institucional, el volumen corresponde a `proyecto-moodle_moodle_data`.

4. Generá un archivo tar comprimido montando el volumen en modo de solo lectura (`:ro`) dentro de un contenedor auxiliar efímero de Alpine:

   ```bash
   sudo docker run --rm \
     -v proyecto-moodle_moodle_data:/datos:ro \
     -v /var/backups/moodle:/respaldos \
     alpine:3.22 \
     tar -czf /respaldos/moodledata_manual_$(date +%Y-%m-%d).tar.gz -C /datos .
   ```

   **Explicación técnica:**
   - `--rm`: Elimina automáticamente el contenedor auxiliar de Alpine al finalizar la compresión.
   - `-v proyecto-moodle_moodle_data:/datos:ro`: Monta el volumen de Moodle en `/datos` como solo lectura, protegiendo los datos contra modificaciones accidentales durante la lectura.
   - `-v /var/backups/moodle:/respaldos`: Monta el directorio seguro de respaldos del host en `/respaldos`.
   - `tar -czf ... -C /datos .`: Comprime el contenido raíz del volumen preservando propietarios, permisos POSIX y marcas de tiempo sin incluir rutas relativas complejas.

5. Reiniciá inmediatamente el servicio de Moodle:

   ```bash
   sudo docker compose start moodle
   ```

6. Verificá que el archivo de respaldo físico se haya generado con tamaño y permisos correctos:

   ```bash
   sudo sh -c 'ls -lh /var/backups/moodle/moodledata_*.tar.gz'
   ```

## Análisis de Contingencia Institucional (RTO y RPO)

Para la infraestructura del Colegio Técnico de Costa Rica, la estrategia de continuidad operativa se articula en los siguientes parámetros:

| Métrica | Meta Institucional CTCR | Mecanismo de Recuperación |
|---|---|---|
| **RPO (Recovery Point Objective)** | **24 Horas** | Cron diario a las 02:00 AM CST con volcado completo de MariaDB (`ctcr_moodle_*.sql.gz`) y retención rotativa de 7 días. |
| **RTO (Recovery Time Objective) — Base de Datos** | **< 15 Minutos** | Importación directa por tubería `gzip -dc | docker compose exec -T db mariadb moodle`. |
| **RTO (Recovery Time Objective) — Sistema Completo** | **< 30 Minutos** | Descompresión de imagen de volumen `moodledata` y restauración del dump SQL en contenedor MariaDB fresco. |

## Correcciones y precauciones aplicables

- **Complementariedad de Respaldos:** La copia en archivo `.tar.gz` del volumen `moodledata` complementa la base de datos relacional, pero **no sustituye** la prueba de restauración SQL en base independiente exigida por la cátedra docente (ejecutada y superada en el subpaso 10-06 con EV-099).
- **Regla 3-2-1 de Respaldos:** Almacenar las copias exclusivamente en `/var/backups/moodle/` dentro del disco virtual de la máquina no protege contra la corrupción del hipervisor o daño del almacenamiento del host. En producción real del CTCR, los archivos `.sql.gz` y `.tar.gz` deben sincronizarse a un servidor de almacenamiento externo o servicio de nube mediante SFTP/rsync cifrado.
- **Espacio en Disco:** La carpeta `moodledata` acumula archivos temporales y cachés en `moodledata/cache/` y `moodledata/localcache/`. Un script de producción avanzado puede excluir dichos directorios (`--exclude='cache/*' --exclude='localcache/*'`) para optimizar espacio y velocidad de transferencia.
