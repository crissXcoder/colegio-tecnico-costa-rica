# PASO 11.02 — Comprobar los servicios del sistema de Ubuntu Server

> **Naturaleza:** procedimiento reproducible derivado íntegramente de la guía compartida, con correcciones para el repositorio.
>
> **Origen:** `docs/fuentes/GUIA-HISTORICA-INTEGRA.md`; pruebas reales de verificación en la VM principal Ubuntu Server.

## Archivos relacionados y por qué importan

- **[`infra/nginx/moodle.conf.example`](../../../infra/nginx/moodle.conf.example)**: VirtualHost de Nginx gestionando TLS y proxy reverso en puertos 80 y 443.
- **[`infra/bind9/named.conf.local.fragment`](../../../infra/bind9/named.conf.local.fragment)**: declaración de zonas maestras DNS institucionales (`ctcr` y `ctcr.test`).
- **[`infra/vsftpd/vsftpd.conf.example`](../../../infra/vsftpd/vsftpd.conf.example)**: configuración del demonio vsftpd con chroot y cifrado FTPS TLSv1.3.
- **[`infra/cron/moodle-backup.cron.example`](../../../infra/cron/moodle-backup.cron.example)**: tarea periódica de respaldo en el demonio Cron.

**Lugar de ejecución:** terminal de Ubuntu Server (`server`, IP `192.168.50.1`).

## Propósito del paso y contexto operacional

Verificar que los cuatro servicios esenciales del host que soportan la plataforma tecnológica del Colegio Técnico de Costa Rica se encuentran activos, inicializados y administrados por `systemd`:
1. **`named` (BIND9):** Servidor DNS autoritativo que resuelve las peticiones hacia `aulavirtual.ctcr` y `moodle.ctcr.test`.
2. **`nginx`:** Proxy inverso y terminador TLS que recibe las conexiones externas en los puertos 80 y 443, redirige a HTTPS y delega el tráfico al backend de Moodle.
3. **`vsftpd`:** Servidor seguro de transferencia de archivos por departamentos bajo FTPS.
4. **`cron`:** Demonio de planificación de tareas periódicas que dispara el respaldo automatizado diario a las 02:00 AM.

## Comprobación recomendada y salida a documentar

1. Consulta del estado de cada unidad systemd mediante `systemctl is-active`.
2. Confirmación de que todas devuelven la cadena exacta `active`.
3. Verificación de que no existan servicios en estado degradado o en bucle de reinicio (`systemctl --failed`).

## Antes de ejecutar

- [ ] Confirmar que no se reiniciaron servicios con configuraciones sintácticamente inválidas.
- [ ] Verificar que Apache2 permanezca detenido y deshabilitado para evitar colisiones en los puertos 80/443.

## Procedimiento completo y comandos originales

1. Consultá el estado de los cuatro servicios del sistema en una sola línea de comprobación:

   ```bash
   systemctl is-active named nginx vsftpd cron
   ```

   **Salida esperada:**
   ```
   active
   active
   active
   active
   ```

2. Alternativamente, podés consultar cada servicio de manera individual:

   ```bash
   sudo systemctl is-active named
   sudo systemctl is-active nginx
   sudo systemctl is-active vsftpd
   sudo systemctl is-active cron
   ```

   Los cuatro comandos deben responder estrictamente `active`.

3. Comprobá que no existan unidades en fallo dentro de systemd:

   ```bash
   systemctl --failed
   ```

   Debe indicar `0 loaded units listed`.

## Correcciones y precauciones aplicables

- **Coexistencia Apache2 vs Nginx:**
  Si `nginx` falla al iniciar (`failed`), la causa más común en este laboratorio es que Apache2 haya sido iniciado accidentalmente ocupando los puertos 80 o 443. En tal caso, debe ejecutarse:
  `sudo systemctl stop apache2 && sudo systemctl disable apache2 && sudo systemctl restart nginx`.
- **Coexistencia BIND9 vs systemd-resolved:**
  BIND9 debe escuchar selectivamente en `192.168.50.1` (`listen-on { 192.168.50.1; };`), dejando el puerto `127.0.0.53:53` libre para el resolutor local de Ubuntu Server.
